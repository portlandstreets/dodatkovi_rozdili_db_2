**Предметна область:** Система управління проектами в корпорації
**Технологічний стек:** PostgreSQL, MongoDB, Neo4j, Python (`psycopg2`, `pymongo`, `neo4j`)

## 1. Види NoSQL баз даних

NoSQL (Not Only SQL) — це підхід до проектування баз даних, який відходить від класичної реляційної табличної схеми для забезпечення горизонтальної масштабованості, гнучкості структури даних та високої продуктивності на спеціалізованих операціях. Основні види NoSQL СУБД поділяються на чотири категорії:

1. **Документоорієнтовані бази даних (Document Stores)**
   * **Приклади:** MongoDB, CouchDB, AWS DocumentDB.
   * **Принцип роботи:** Зберігають інформацію у вигляді напівструктурованих документів (зазвичай у форматах JSON, BSON або XML). Кожен документ є самодостатнім агрегатом, який може містити вкладені об'єкти та масиви довільної глибини.
   * **Сценарії використання:** Зберігання карток товарів або задач зі змінною кількістю атрибутів, систем керування контентом (CMS), логів подій, каталогів і профілів користувачів.

2. **Бази даних типу «Ключ-значення» (Key-Value Stores)**
   * **Приклади:** Redis, Memcached, Amazon DynamoDB.
   * **Принцип роботи:** Використовують асоціативний масив (хеш-таблицю), де кожному унікальному ключу відповідає певне значення (рядок, бінарний об'єкт, список або множина). Забезпечують константну складність доступу до даних $O(1)$ за рахунок розміщення в оперативній пам'яті.
   * **Сценарії використання:** Кешування результатів важких запитів, зберігання сесій авторизації, лічильники реального часу, розподілені блокування (Distributed Locks) та черги повідомлень.

3. **Колонкові бази даних (Wide-Column Stores)**
   * **Приклади:** Apache Cassandra, ScyllaDB, HBase.
   * **Принцип роботи:** Дані зберігаються не по рядках, а за родинами колонок (Column Families). Кожен запис може мати різний набір колонок, а фізичне групування даних за стовпцями дозволяє надзвичайно швидко виконувати агрегацію та масовий послідовний запис.
   * **Сценарії використання:** Зберігання часових рядів (Time-Series), телеметрія IoT-пристроїв, системи моніторингу, фінансовий аудит та аналітика великих обсягів даних (Big Data).

4. **Графові бази даних (Graph Databases)**
   * **Приклади:** Neo4j, ArangoDB, Amazon Neptune.
   * **Принцип роботи:** Представляють дані у вигляді математичного графа, який складається з вузлів (Nodes — сутностей) та спрямованих ребер (Edges / Relationships — зв'язків між ними). Як вузли, так і ребра можуть мати власні атрибути (Properties). Обхід графа виконується за прямими вказівниками без обчислення індексних з'єднань.
   * **Сценарії використання:** Моделювання складних ієрархій, мереж залежностей між задачами (Critical Path Method), організаційних структур, систем рекомендацій та виявлення шахрайських схем.

## 2. Обґрунтування винесення частини даних у NoSQL

У межах предметної області «Система управління проектами в корпорації» ядро бізнес-логіки — фінансовий облік бюджетів (`project_budgets`), договори з клієнтами (`clients`), штатний розпис та погодинні ставки працівників (`employees`, `positions`) — вимагає суворої транзакційної узгодженості (ACID) та реляційної цілісності, тому його доцільно залишити в реляційній СУБД **PostgreSQL**.

Водночас винесення підсистеми **детальної картки задачі, журналу аудиту змін та обговорень із вкладеними файлами** у документоорієнтовану базу даних **MongoDB** є архітектурно більш ефективним з таких причин:

1. **Усунення операцій багатотабличного з'єднання (JOIN Elimination) та локальність даних:**
   * У нормалізованій реляційній схемі (3NF) інформація про одну задачу розподілена щонайменше між чотирма таблицями: базові атрибути задачі (`tasks`), історія змін (`task_audit`), коментарі (`comments`) та прикріплені файли (`attachments`). Для кожного відображення картки задачі користувачеві реляційна СУБД виконує три операції `JOIN`.
   * У MongoDB картка задачі разом із масивом історії змін та списком коментарів з файлами зберігається як єдиний BSON-документ. Фізично на диску ці дані розташовані неперервно (Data Locality), що дозволяє зчитати всю сутність за одне звернення за первинним ключем `_id`.

2. **Поліморфність структури записів аудиту та метаданих (Schema Flexibility):**
   * Події, що відбуваються із задачею під час життєвого циклу, мають різний набір атрибутів: зміна статусу містить поля `old_status` і `new_status`, логування часу — `hours_spent` і `work_date`, а зміна виконавця — `previous_assignee` та `new_assignee`. У реляційній базі це призводить або до створення розрідженої таблиці з великою кількістю `NULL`-полів, або до ускладнення схеми додатковими таблицями. Документна модель природно приймає об'єкти довільної структури в масиві `audit`.

3. **Ізоляція високочастотного навантаження на запис і читання:**
   * Коментарі та автоматичні записи аудиту генерують постійний потік операцій дописування (Append-heavy workload), а відкриття карток задач розробниками створює основне навантаження на читання. Винесення цього модуля в MongoDB розвантажує транзакційне ядро PostgreSQL, залишаючи ресурси реляційної бази для критичних фінансових розрахунків.

Додатково, для підсистеми **аналізу залежностей між задачами (`task_dependencies`) та матриці розподілу команд** доцільним є використання графової СУБД **Neo4j**, оскільки пошук блокуючих ланцюжків довільної глибини у графі виконується без рекурсивних SQL-запитів (`WITH RECURSIVE`).

## 3. Реалізація моделей даних у NoSQL (MongoDB) та SQL (PostgreSQL)

### 3.1. Документна модель у MongoDB (Колекція `task_cards`)
Уся пов'язана інформація інкапсульована в одному документі:

```json
{
  "_id": "TASK-1",
  "project_id": 1,
  "title": "Task number 1",
  "status": "IN_PROGRESS",
  "assignee_id": 2,
  "audit": [
    {"action": "UPDATE", "step": 0, "ts": 1731333600.0},
    {"action": "UPDATE", "step": 1, "ts": 1731333605.0}
  ],
  "comments": [
    {
      "author_id": 1,
      "body": "Comment 0",
      "attachment": "file.pdf"
    }
  ]
}
